# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"مراحل" (Marahil) — an Arabic-language (RTL), interactive tutoring/course platform covering every school stage (kindergarten through university and professional training), with quizzes, progress tracking, and auto-issued digital certificates with QR-code verification.

The repo is a monorepo with two independently deployed halves:

- **`frontend/`** — Next.js 16 (App Router, TypeScript, Tailwind CSS v4). Deployed to Vercel with **Root Directory = `frontend`**.
- **`backend/`** — Firebase project config: Firestore/Storage security rules only. Deployed via `firebase deploy` run from inside `backend/` (project id `marahil-2026`, set in `backend/.firebaserc`).
- **`design-reference/`** — a static JSX mockup from an earlier, unrelated concept ("أُفُق"/Ofoq). Kept only as a visual reference; not imported or built by anything.

There is no separate Node/Express backend, and **no Cloud Functions** — the project intentionally stays on Firebase's free Spark plan (no billing account attached), so Auth + Firestore + Firestore security rules *are* the entire backend. The one exception is `frontend/src/app/api/upload/route.ts`, a single Vercel serverless API route (see "Image uploads" below) — that's Vercel infrastructure that ships with every Next.js app regardless, not a Firebase Cloud Function, so it doesn't touch the Spark-plan constraint.

## Commands

Run from `frontend/`:
- `npm run dev` — dev server (Turbopack)
- `npm run build` — production build (also runs the TypeScript check)
- `npm run lint` — ESLint

Run from `backend/` (requires `firebase login` once):
- `firebase deploy` — deploys Firestore rules, indexes, and Storage rules together
- `firebase deploy --only firestore:rules` — deploy just the rules (the usual case)

## Architecture

### Data model (Firestore)

- `users/{uid}` — `{ name, email, role: "teacher"|"student"|"admin", photoURL?, createdAt }`. `role` can only be `"admin"` if another admin (or a human editing Firestore directly in the Firebase Console) set it that way — no client-side `create` path ever allows `role: "admin"`, so the first admin always has to be bootstrapped by hand-editing their `users/{uid}` doc in the Console after they register normally.
- `courses/{courseId}` — `{ title, description, stage, subject, teacherId, teacherName, published, lessonsCount, studentsCount, createdAt }`
  - `courses/{courseId}/lessons/{lessonId}` — `{ title, order, videoUrl?, content?, quiz?: QuizQuestion[] }`. A lesson either has a quiz (graded, drives progress) or is marked complete manually.
- `enrollments/{uid}_{courseId}` — one doc per student per course; id is deterministic (`uid_courseId`), not auto-generated. Tracks `completedLessonIds`, `quizScores`, `progress` (0–100), `certificateIssued`.
- `certificates/{uid}_{courseId}` — `{ uid, studentName, courseId, courseTitle, teacherName, serial, verifyCode, issuedAt }`. Same deterministic-id scheme as `enrollments`. Publicly readable (verification page needs it).

### Certificates are issued client-side, but gated entirely by Firestore rules — read `backend/firestore.rules` before touching this

There's no Cloud Function (see above — free plan, no billing account), so `frontend/src/lib/firebase/certificates.ts`'s `issueCertificate()` writes the `certificates` doc directly from the browser once `frontend/src/lib/hooks/useLessonPlayer.ts` sees `enrollment.progress` hit 100. The only thing standing between that and a student forging their own certificate is `backend/firestore.rules`:

- the `enrollments` update rule caps `completedLessonIds.size()` at the course's real `lessonsCount` and only allows `progress == 100` once that count is actually reached, and only allows `certificateIssued` to flip false→true (never back);
- the `certificates` create rule re-derives `studentName`/`courseTitle`/`teacherName` from the real `users`/`courses` docs via `get()` (a client can't write fake display text onto its own certificate), and requires the matching `enrollments/{uid}_{courseId}` doc to already show `progress == 100`.

This is a deliberate trade-off, not an oversight: it's not as airtight as a server-side issuer (a sufficiently motivated user could still pad `completedLessonIds` with fabricated ids up to the real count, since rules can't iterate the `lessons` subcollection to check each id is real), but it needs no billing account. If that gap ever matters, the fix is a Blaze-plan Cloud Function trigger on `enrollments` writes that issues the certificate via the Admin SDK instead — don't try to close it further with more rules; Firestore rules can't enumerate a subcollection's real ids.

If you change how progress/completion is computed, keep the invariant that `enrollments.progress` can only reach 100 in lockstep with the rules' `completedLessonIds.size()` check.

### Admin role is a Firestore-based bypass, not a Firebase Auth custom claim

There's no Admin SDK (see above), so there's no way to set a real Firebase custom claim from this codebase either — `isAdmin()` in `backend/firestore.rules` just checks `role == 'admin'` on the requester's own `users/{uid}` doc via `get()`, the same pattern `courseData()`/`userData()` already used. It's additive-only (`|| isAdmin()`) on top of every existing rule; no owner-only check was removed. `users` read/update, `courses` read, and `enrollments` read all have an admin bypass. The admin dashboard (`/dashboard/admin/users`) can promote/demote any user's `role`, but can't delete a Firebase Auth account or the user's own admin status from someone else without going through the same role-update path — and nothing here can hard-delete a Firebase Auth account at all (needs the Admin SDK); removing a user fully still requires the Firebase Console.

**Disabling a user is a separate `disabled: boolean` kill switch, not a `status` value.** `status` (`pending`/`approved`) stays scoped to the teacher-approval workflow; overloading it for "disabled" would have thrown away a pending teacher's approval state the moment an admin disabled them. `setUserDisabled()` in `lib/firebase/users.ts` just flips `disabled` on the user's own doc; `isApproved(uid)` in `backend/firestore.rules` now also returns `false` once `disabled == true` (any role), so the exact same rule that blocks an unapproved teacher from creating a course now also blocks a disabled teacher from editing an existing course/lesson and blocks a disabled student from creating or advancing an enrollment — no separate gate to keep in sync. On the client, `isAccountDisabled()` (`lib/utils/userStatus.ts`) is checked in `RoleGuard.tsx` the same way `isPendingTeacher()` already was, redirecting to `/auth/account-disabled` (`AccountDisabledNotice.tsx`, mirroring `PendingApprovalNotice.tsx`) instead of a role's dashboard.

**One account is hardcoded as un-demotable and un-disableable: `eldesouky71@gmail.com`** (`PROTECTED_ADMIN_EMAIL` in `frontend/src/lib/constants.ts`). The real enforcement is `isProtectedAccount()` in `backend/firestore.rules`, which the `users` update rule consults to refuse any write — from any admin, including the account itself — that changes that email's `role`, `disabled`, or `email` field; every other field on it (name, photo, personal details) stays normally admin-editable. Rules can't import the frontend constant, so the email is a literal there too — keep both in sync if it ever changes. Only a human editing Firestore directly in the Firebase Console bypasses this, same as every other rules-enforced constraint in this project.

`AdminUsersView`/`AdminUserRow` also cover the rest of what's achievable for user management without the Admin SDK: role/status/statusFilter + search + sort filtering is all client-side over the one `listAllUsers()` fetch (no pagination — fine at this project's scale, revisit if the users collection gets large); bulk select drives `handleBulkDisable` writing every selected user's `disabled` field in parallel, then calls `refresh()` and bumps a `listVersion` counter used in each row's `key` to force a remount — needed because each row otherwise owns its role/status/disabled as local `useState`, seeded once from props, which a parent-triggered refetch alone wouldn't re-sync; "reset password" just calls the existing `resetPassword()` (`sendPasswordResetEmail`) with the target's email — Firebase sends that regardless of who's signed in, so no special admin path was needed. What's still impossible on Spark and isn't attempted: hard-deleting a Firebase Auth account and sending any email/notification that isn't Firebase's own hosted flow (both need the Admin SDK / Cloud Functions).

**Export is `.xlsx`, not CSV** — `lib/utils/exportExcel.ts` wraps SheetJS (`xlsx` on npm). That package has two open advisories (prototype pollution, ReDoS) with no fix released on the npm registry; both are in the *parser*, and this call path is write-only (builds a workbook from our own trusted data, never parses a user-supplied file), so the actual exposure here is effectively nil — but don't repurpose `downloadExcel()` or add an "import from Excel" feature on top of this same dependency without re-reading those advisories first.

**`AdminUserRow`'s per-row controls are split into "primary" (always visible: role select, approve if pending, disable/enable) and "secondary" (collapsed into a `⋮` `ActionsMenu` — reset password, view details, delete)** — a plain `useState` + outside-click-listener dropdown local to that file, not a shared `ui/` component (nothing else needs one yet). Delete still can't fire directly from the menu — clicking it only sets `confirmingDelete`, which renders the confirm/cancel row outside the menu (a menu item can't stay open through its own confirmation step, since every item click closes the menu first).

**`age` is teacher/admin's only *derived* `PersonalDetails` field** — `lib/utils/nationalId.ts`'s `parseEgyptianNationalId()` decodes an Egyptian national ID's embedded birth date (century digit + YYMMDD, positions 1–7) into an age, computed client-side, purely structural (regex + date-range checks) — it deliberately does **not** verify the ID's own check digit, since getting that checksum subtly wrong would reject genuinely valid IDs, which is worse than not checking it at all. `PersonalDetailsForm.tsx` (signup) and `ProfileEditForm.tsx` (settings, `profile.role === "teacher" || "admin"`) both render the `age` `FormField` as a disabled, auto-filled input for teacher/admin and a normal editable one for student — same branch condition (`hasNationalId`), duplicated across the two forms rather than shared, since they don't otherwise share form state. A student never sees a national-ID field at all (none is collected for that role); nothing enforces this at the rules layer, since it's purely a UI/UX choice, not a security boundary.

### Auth flows: email/password, Google, forgot-password, complete-profile

`lib/firebase/auth.ts` has both `registerUser`/`loginUser` (email/password) and `signInWithGoogle()` (`GoogleAuthProvider` + `signInWithPopup`) — enabling the Google provider itself is a one-time manual step in Firebase Console → Authentication → Sign-in method, no code does it. Google sign-in has no role, so a first-time Google user has no `users/{uid}` doc yet; `RoleGuard.tsx` distinguishes this from "not signed in" by checking `firebaseUser` (from `useAuth()`) separately from `profile` — no `firebaseUser` → `/auth/login`, `firebaseUser` but no `profile` → `/auth/complete-profile`, `profile.role` mismatch → the user's own dashboard. `GoogleSignInButton.tsx` (shared by `LoginForm`/`RegisterForm`, since the post-sign-in branch is identical either way) does the same `getUserProfile` check right after sign-in to route directly. `resetPassword()` wraps `sendPasswordResetEmail`; the actual reset UI is Firebase's own default hosted action page, not a custom in-app route — deliberate, to avoid building `oobCode`/`confirmPasswordReset` handling for a Spark-plan project that otherwise has no server code.

`CompleteProfileForm.tsx` pre-fills `name` from `firebaseUser.displayName` and, on submit, passes `photoURL: firebaseUser.photoURL ?? undefined` into `createUserProfile()` — so a first-time Google sign-in's avatar gets copied into the `users/{uid}` doc at account creation. `createUserProfile()`/`updateUserProfileFields()` both route their payload through `withoutUndefined()` in `lib/firebase/users.ts` first — Firestore's `setDoc`/`updateDoc` throw on an explicit `undefined` field, which `photoURL` (absent for email/password sign-ups) and any blank optional detail would otherwise be. **`GoogleSignInButton.tsx` also backfills the photo on every subsequent Google sign-in, but only when the existing profile has no `photoURL` at all** (`updateUserPhoto()`, guarded by `!profile.photoURL`) — covers accounts created before this existed, or any other way one ended up with none, without ever overwriting a photo the user later uploaded to R2 through `ProfileView` back to their Google one.

`/profile` (`ProfileView.tsx`) is a full self-service settings page, not just an avatar/read-only view: `ProfileEditForm.tsx` lets a user edit their own name and role-specific personal details (same per-role field set as the signup wizard's `PersonalDetailsForm.tsx`, but pre-filled and single-step) via `updateUserProfileFields()` — clearing an optional field sends Firestore's `deleteField()` for it rather than silently keeping the stale value, since `updateDoc` just skips over keys with `undefined`. `ChangePasswordCard.tsx` reuses the same `resetPassword()` email-link flow as `ForgotPasswordForm`/the admin's per-user reset button (no re-auth flow needed) and only renders when `firebaseUser.providerData` includes the `password` provider — a Google-only account has nothing to reset.

### Image uploads (course cover, lesson image, avatar) go through Cloudflare R2, not Firebase Storage

`courses.coverImageUrl`, `lessons.imageUrl`, and `users.photoURL` (the last already existed for Google sign-in) can all point at an image in a Cloudflare R2 bucket instead of/alongside the defaults (`coverIcon` stays as the always-present fallback when no cover image was uploaded). `frontend/src/lib/firebase/client.ts` still initializes Firebase Storage, but it's unused — R2 is cheaper and this avoids a second security-rules surface to maintain.

The R2 secret access key can never reach the browser, so uploads go through the app's only server-side code, `app/api/upload/route.ts`: the client asks it for a short-lived presigned PUT URL (`@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` against R2's S3-compatible endpoint), then uploads the file bytes straight to R2 from the browser — the file never passes through the Vercel function, avoiding its request-body size limit. Auth on that route is checked **without the Admin SDK**: it calls Firebase's own public Identity Toolkit REST endpoint (`identitytoolkit.googleapis.com/v1/accounts:lookup`) to verify the caller's ID token, the same "no service account" posture as everywhere else in this project. `frontend/src/lib/upload/uploadImage.ts` is the one client-side entry point every upload UI calls (`components/ui/ImageUploadField.tsx`); don't call `/api/upload` directly from a new call site.

Env vars `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET_NAME` / `R2_PUBLIC_URL` are server-only (no `NEXT_PUBLIC_` prefix — see `.env.example`) and live in Vercel's project env vars plus local `.env.local`, never committed. `next.config.ts`'s `images.remotePatterns` has to list both the R2 public host and `lh3.googleusercontent.com` (Google avatar photos) for `next/image` to render them.

### `SiteChrome` renders one sidebar shell for the whole signed-in experience, not just `/dashboard/*`

**`components/layout/SiteChrome.tsx` — not any per-route layout — decides whether a request gets the public `Navbar`/`Footer` or `DashboardShell` (sidebar + topbar), and it now makes that call for every route in the app, not just `/dashboard/*`.** A signed-in user with a complete, approved, non-disabled profile gets the sidebar shell on `/profile`, `/courses`, `/verify`, `/certificates/[id]`, `/learn/**` — not only inside `/dashboard/*`. **The one deliberate exception is the bare home page `/` itself** (alongside `/auth/*`, kept plain since mid sign-up isn't "in the app" yet): `DashboardSidebar.tsx`'s own `nav.siteHome` link points there, and that link means "step out of the app" — if `/` also got the app shell, clicking it would leave the dashboard topbar sitting on top of the marketing Hero, defeating the point of the link (this was a real shipped bug: an admin's topbar/search bar rendered above the landing page). `app/[locale]/dashboard/{admin,teacher,student}/layout.tsx` are now just a one-line `RoleGuard` each; they used to also render `DashboardShell` themselves, which would now double it up under `/dashboard/*` since `SiteChrome` already does. The per-role sidebar config (`navItems`, `homeHref`, `roleLabel`) moved out of those three layout files into `lib/hooks/useDashboardShellConfig.ts`, a hook keyed off `useAuth().profile.role`, so `SiteChrome` can build the same config regardless of which route triggered it. `Footer.tsx` had to become a client component (`useTranslations` instead of the server-side `getTranslations`) so `SiteChrome` — a client component, since it needs `usePathname()` and `useAuth()` — can conditionally render it.

Because `/` and `/auth/*` keep the public `Navbar` for a signed-in user too, `Navbar.tsx`'s own mobile drawer has to independently stay a complete, correct account menu — dashboard, profile, **and logout** — not a stripped-down version of the sidebar; it was shipped once missing logout entirely (a signed-in visitor landing on `/` had no way to sign out from mobile) and once missing the signed-out `login` link (`startNow` only). Its signed-in section is styled to match `DashboardSidebar.tsx`'s nav-item look (rounded-xl row, icon + label, `hover:bg-surface-2`) even though the two aren't the same component — "unify" here means visual consistency between the two nav surfaces, not merging them into one.

While `loading` (auth still resolving) or for a signed-out visitor, `SiteChrome` falls back to the public `Navbar`/`Footer` — same as `Navbar`'s own existing default-to-signed-out rendering during `loading`, so there's no new flash of the wrong chrome introduced here. A handful of pages (`/profile`, `/courses`, `/verify`, `/certificates/[id]`) still carry their own `<section><Container>` padding from when they were *only* ever reached through the public chrome; when a signed-in user hits them now, that stacks with `DashboardShell`'s own `<main className="p-5 md:p-8">` padding — extra whitespace, not breakage, and an acceptable trade-off for now rather than rewriting every dual-mode page's layout.

`DashboardSidebar.tsx` is fixed-positioned with Tailwind's logical-property utilities (`start-0`, `ms-64`, `ltr:-translate-x-full rtl:translate-x-full` for the mobile off-canvas state) rather than literal `left`/`right`/`margin-right` — this is the same convention `Hero.tsx`/`FinalCta.tsx`/`LessonPlayer.tsx` already use, and matters here specifically because the sidebar has to swap sides between the `ar` and `en` locales. `useDashboardShellConfig`'s per-role `navItems` hold only that role's own pages (dashboard home first, labeled via the shared `nav.dashboard` key so the wording is identical across all three) — **`navItems` deliberately excludes `/` and `/profile`**: `DashboardSidebar.tsx` itself renders a `nav.siteHome` link back to `/` as the very first item, *above* the role's own `navItems`, and a `nav.profile` link in the footer, above logout. All three (site-home, profile, logout) are sourced from the `nav` namespace directly inside `DashboardSidebar.tsx` rather than threaded through as props or duplicated per role, so every role is guaranteed the identical links in the identical positions — don't add a `/profile` entry back into a role's own `navItems` array, it'd just show up twice.

`DashboardTopbar.tsx` has no search box (it was admin-only and duplicated the search already on `AdminUsersView` itself — see `dashboardAdmin.users.searchPlaceholder` vs. the now-deleted `dashboardAdmin.topbar` key) and no separate hamburger button — `Logo.tsx` sits at the start of the bar, and the profile chip itself is the mobile sidebar trigger (`onClick={onMenuClick}`; a no-op on desktop, where the sidebar is always visible regardless of the open/close state, so leaving the handler unconditional is harmless).

This used to be admin-only (`AdminShell`/`AdminSidebar`/`AdminTopbar`, teacher/student had no sidebar at all, and everyone — including admin — also got the public `Navbar` stacked on top, each with its own mobile drawer and logout: the original "2 sidebars" bug).

The two overview charts (`AdminChart.tsx`, a thin Chart.js wrapper) are built with the `dataviz` skill's method — load that skill again before touching chart colors or adding a new chart, don't hand-pick colors.

### Landing page motion: `framer-motion` for micro-interactions, GSAP ScrollTrigger for scroll reveals, Lenis for smooth scroll — public pages only

`components/landing/ScrollReveal.tsx` wraps a section's repeated children (a features grid, a steps grid, a heading+CTA block) and fades/slides each one up once as it scrolls into view, via `ScrollTrigger.batch` — it treats every *direct child* of the wrapped element as its own staggered target, so wrap only the actual repeated-item container, not a whole section (a step's connecting dashed-line div counts as a target too if it's a sibling inside the wrapped div — harmless, it just fades in with the steps). `gsap.registerPlugin(ScrollTrigger)` is guarded behind `typeof window !== "undefined"` at module scope, and the reveal itself no-ops under `prefers-reduced-motion`. It only ever runs once per mount (no `dependencies` passed to `useGSAP`), so `StagesSection.tsx`'s subject-tag row — which re-renders with different tags on every tab click — is deliberately left *outside* `ScrollReveal`; only its stable tab-button row is wrapped, so switching tabs never fights a one-time reveal animation.

`components/layout/LenisProvider.tsx` wraps only `SiteChrome`'s public-chrome branch (`Navbar`/`Footer`), never `DashboardShell` — Lenis-style scroll smoothing is a known anti-pattern over data-heavy lists/tables, which is most of the dashboard now that the sidebar wraps it. It drives Lenis off `gsap.ticker` (the officially documented GSAP+Lenis integration: `gsap.ticker.add((time) => lenis.raf(time * 1000))`, `gsap.ticker.lagSmoothing(0)`, and `lenis.on("scroll", ScrollTrigger.update)` to keep ScrollTrigger's positions in sync with Lenis's virtual scroll) rather than its own `requestAnimationFrame` loop, so it shares one rAF driver with the ScrollTrigger reveals instead of running a second one. Skipped under `prefers-reduced-motion`, same as `ScrollReveal`.

### Motion and 3D: `framer-motion` site-wide, `three`/`@react-three/fiber` only on the Hero, `canvas-confetti` on certificates

`Button.tsx` and `StatCard.tsx` are `motion.button`/`motion.div` under the hood now — **both need their own `"use client"`, independent of whichever page renders them**, since a `motion.*` component throws ("createMotionComponent() from the server") the moment any of its callers sits behind a Server Component boundary without the child itself being an explicit Client Component; the file that defines the `motion.*` usage is what needs the directive, not just its callers. `ButtonProps` also has to `Omit` `onDrag`/`onDragStart`/`onDragEnd`/`onAnimationStart`/`onAnimationEnd` from `ButtonHTMLAttributes` — framer-motion's own gesture-handler props of the same name have an incompatible signature, so spreading native DOM props into `motion.button` fails to typecheck otherwise. `DashboardShell.tsx`'s `<main>` wraps `{children}` in `AnimatePresence`/`motion.div` keyed by `usePathname()` for a fade between pages — this now covers every route the shell wraps (see above), not just `/dashboard/*`.

`components/landing/Hero3D.tsx` is the only place `three`/`@react-three/fiber`/`@react-three/drei` are used — a real 5-point star (built from a `THREE.Shape` + `ExtrudeGeometry`, then `.center()`-ed, not an icosahedron — an abstract gem didn't read as "the logo's star" to an actual viewer) orbited by a thin ring, rendered via `Hero3DScene.tsx`, loaded through `next/dynamic(..., { ssr: false })` since `Canvas` needs the browser. The star's material color is a hardcoded `{light, dark}` table copied from `globals.css`'s `--gold`/`--accent` (same "canvas can't resolve `var()`" constraint as `chartColors.ts`/`useQrCode.ts` — see the visual-design section above), picked by `useTheme()` as a plain derived value rather than synced via `useEffect` + `getComputedStyle`, specifically to avoid a `setState`-in-effect lint error and stay reactive to theme without an extra render pass. **The scene's lights are a fixed neutral white, not brand-colored** — a colored directional light multiplies with the material's own color, which is what was turning the gold star muddy brown before this was corrected; don't tint these lights to "match the theme" again without checking the rendered result. No drei `<Environment>` — it fetches an HDR map from an external CDN on every load, which this project avoids everywhere else too (R2 for images, no other external asset CDNs). Rotation is skipped when `prefers-reduced-motion` is set, checked once via a lazy `useState` initializer (safe because this component only ever mounts client-side).

`CertificateView.tsx` fires a one-time `canvas-confetti` burst (brand colors, same `getComputedStyle` pattern as `chartColors.ts` — this one doesn't need the theme-reactive-without-effect treatment `Hero3D` does, since it only ever reads colors once per certificate load inside a `useEffect` that already has a real external side effect to perform, not just a state sync) when a certificate finishes loading, skipped under `prefers-reduced-motion`, guarded by a `useRef` so it can't refire on an unrelated re-render.

GSAP/ScrollTrigger and Lenis (smooth-scroll) were deliberately **not** added in this pass — Lenis-style scroll-jacking is a known anti-pattern over data-heavy lists/tables (which is most of the admin dashboard now that the sidebar wraps it), and GSAP's ScrollTrigger earns its complexity on a scroll-driven marketing sequence the landing page isn't structured for yet. Revisit only if the landing page itself gets restructured around scroll storytelling.

### Frontend structure (`frontend/src/`)

Small, single-purpose files by convention — prefer adding a new file over growing an existing one.

- `app/[locale]/` — every route is nested under a `[locale]` segment (`ar`/`en`, see i18n below); there is no un-localized `app/` route. Each `page.tsx` is a thin wrapper that awaits `params` (Next 16: `params` is a `Promise`, and now also carries `locale`) and renders one component from `components/`. No business logic in `app/`. Lesson playback lives at `learn/[courseId]/[lessonId]`, not `lesson/` (that name is reserved for the `components/lesson/` group below). `profile/` (no `[locale]` inside it — it's a locale-scoped route like the rest, just role-agnostic, unlike everything under `dashboard/`) is the one signed-in page not gated by `RoleGuard`.
- `app/api/` — server-only route handlers, outside `[locale]` (API routes aren't localized pages). Currently just `upload/route.ts` — see "Image uploads" above before adding another one.
- `components/` — grouped by feature: `landing/`, `auth/` (also `GoogleSignInButton`, `ForgotPasswordForm`, `CompleteProfileForm`, `PendingApprovalNotice`, `AccountDisabledNotice`, `ContactAdminNotice`, `AuthGate`, `PersonalDetailsForm`), `courses/`, `lesson/`, `quiz/`, `certificates/`, `profile/` (`ProfileView`, `ProfileEditForm`, `ChangePasswordCard`), `dashboard/` (role-shared: `DashboardHeader`, `StatCard`, `DashboardShell`/`DashboardSidebar`/`DashboardTopbar`), `dashboard/teacher/`, `dashboard/student/`, `dashboard/admin/` (also `AdminChart`), `layout/` (also `SiteChrome`), `theme/` (`ThemeToggle`, `ThemeScript`, `LanguageSwitcher`), `analytics/` (`AnalyticsInit`), `ui/` (generic primitives: `Button`, `Card`, `Badge`, `ProgressBar`, `Spinner`, `Container`, `FormField`, `ImageUploadField`).
- `lib/firebase/` — one file per collection/concern (`auth.ts`, `users.ts`, `courses.ts`, `enrollments.ts`, `certificates.ts`, `stages.ts`, `auditLog.ts`, `analytics.ts`, `client.ts` for SDK init). This is the only layer allowed to import from `firebase/*`.
- `lib/upload/` — `uploadImage.ts`, the R2 upload client (see "Image uploads" above). Not a Firebase concern, so it's deliberately outside `lib/firebase/`.
- `lib/hooks/` — one `useX` hook per screen/concern, each wrapping a `lib/firebase/*` call in loading/state management (e.g. `useCourseDetail`, `useEnrollment`, `useLessonPlayer`, `useTeacherCourses`). Components call hooks; hooks call `lib/firebase/*`; components never import `lib/firebase/*` directly.
- `context/` — global state: `AuthProvider.tsx` (Firebase auth user + Firestore profile + role, read via `useAuth()`) and `ThemeProvider.tsx` (light/dark, read via `useTheme()`).
- `types/` — one file per domain type (`course.ts`, `user.ts`, `quiz.ts`, `certificate.ts`, `stage.ts`).
- `data/stages.ts` — static list of school stages/subjects, used both by the landing page and the course-creation/filter UI. Edit here to add a stage or subject, not in components.
- `data/governorates.ts` — Egypt's 27 governorates (`GOVERNORATE_IDS`), same static-list-plus-translated-label pattern as stages (`lib/hooks/useGovernorates.ts` mirrors `useStages.ts`/`useStageLabel()`). `PersonalDetails.governorate` stores the id (e.g. `"cairo"`), not the label — `useGovernorateLabel()` translates an id back to a label for display (admin user details, the Excel export), and falls back to the raw stored value for pre-existing free-text governorate data written before this was a dropdown.

Role-gating: `components/auth/RoleGuard.tsx` is called once per role, in that role's `dashboard/{admin,teacher,student}/layout.tsx`, and redirects based on `useAuth().profile.role`. There's no middleware-based *auth* protection — it's all client-side via this guard plus the Firestore rules being the real enforcement layer. (`proxy.ts` does exist, but it's `next-intl`'s locale-routing middleware, unrelated to auth — see below.)

**`components/auth/AuthGate.tsx` is the site-wide version of that same three-way check — no profile yet / pending teacher / disabled — mounted once in `app/[locale]/layout.tsx` above `SiteChrome`, not scoped to `/dashboard/*` like `RoleGuard`.** A signed-in user in one of those three states gets redirected off of *any* route except `/auth/*` (so the target pages themselves, and everything under `/auth/`, stay reachable) — not just kept out of the dashboard, kept out of the whole app: browsing `/courses` or even `/` with an incomplete profile bounces you to `/auth/complete-profile` first. `RoleGuard` no longer issues those three redirects itself (to avoid racing `AuthGate` to two different targets on the same tick) — it still blocks *rendering* on the same conditions, so dashboard content doesn't flash before `AuthGate`'s effect fires, but the actual redirect for no-profile/pending/disabled is `AuthGate`'s job everywhere, `RoleGuard`'s only remaining redirects are signed-out → login and wrong-role → the user's own dashboard. `PendingApprovalNotice.tsx`/`AccountDisabledNotice.tsx`/`CompleteProfileForm.tsx` each still redirect *away* from their own `/auth/*` page once its condition no longer applies (e.g. an approved teacher clicking "check again") — that part was never `AuthGate`'s job, since `/auth/*` is exempt from it.

Both of those notice pages also render `ContactAdminNotice.tsx` (a `mailto:` link to `SUPPORT_EMAIL` in `lib/constants.ts`, currently the same address as `PROTECTED_ADMIN_EMAIL` but kept as a separate constant in case support should ever go through a different inbox) — a pending or disabled account needs a way to actually reach the admin, not just be told to.

i18n: routing/UI text is bilingual (Arabic default, English) via `next-intl`. `i18n/routing.ts` defines `locales: ["ar", "en"]`, `defaultLocale: "ar"`, `localePrefix: "always"`; `i18n/navigation.ts` exports locale-aware `Link`/`useRouter`/etc. to use instead of Next's own; `i18n/request.ts` resolves the active locale server-side. `proxy.ts` at the `src/` root (Next 16's rename of `middleware.ts` — same convention, new filename) runs `next-intl`'s middleware to redirect bare paths to a locale prefix. Copy is in `messages/ar.json` and `messages/en.json` — add new strings to both, don't hardcode UI text in components. `app/[locale]/layout.tsx` sets `dir="rtl"|"ltr"` from the locale and loads fonts.

Visual design: the whole app is driven by semantic CSS custom properties defined once in `app/globals.css` (`--bg`, `--surface`, `--heading`, `--body`, `--primary`, `--accent`, `--gold`, `--danger`, `--success`, etc.), re-exposed as Tailwind utilities via a Tailwind v4 `@theme inline` block (so `bg-primary`, `text-heading`, `border-gold/40` etc. just work) — there's no `tailwind.config` theme extension. Components essentially never hardcode a hex color; the only exceptions are `Constellation.tsx`'s canvas-rendering fallback constants, `useQrCode.ts`'s QR-library color option (the `qrcode` package needs literal hex, not `var()`), `GoogleSignInButton.tsx`'s inline Google "G" mark (Google's brand colors are fixed, not themeable), `lib/utils/chartColors.ts` reading the `--chart-1/2/3` tokens via `getComputedStyle` for the same reason (Chart.js draws to canvas, which can't resolve `var()`), `Hero3DScene.tsx`'s hardcoded `{light, dark}` color table and `CertificateView.tsx`'s confetti colors (WebGL/canvas, same constraint — see the Motion and 3D section below), and any inline `style={{ backgroundImage: "linear-gradient(..., var(--primary), ...)" }}` gradients that Tailwind utilities can't express — all still source the actual app colors from the same tokens wherever the app's own palette is involved. When adding a new color, add the token to `globals.css` (both the light `:root` block and the `[data-theme="dark"]` block) and its `--color-*` mapping in `@theme inline`, not a one-off arbitrary-value class. The brand palette is deep navy blue (`--primary`, trust/knowledge), teal (`--accent`, growth), and gold (`--gold`, achievement — the star in the logo); see `public/brand/`. `--chart-1/2/3` are a separate categorical triplet just for Chart.js marks — `--primary` itself is too dark to pass a chart mark's lightness band, so don't reuse it there; re-validate with the `dataviz` skill's `validate_palette.js` before changing any of the three.

Fonts: Cairo (Arabic + Latin) is the default for both `--font-display` and `--font-body`; an `html[lang="en"]` override in `globals.css` swaps to Poppins (with Cairo as fallback) for the English locale, per the brand typography spec. Both are loaded via `next/font/google` in `app/[locale]/layout.tsx` — don't reintroduce a manual `@import` for them in CSS (breaks `@import`-must-be-first CSS ordering with Tailwind's own `@import "tailwindcss"`).

Light/dark theme is a `data-theme` attribute on `<html>`, toggled by `ThemeProvider`/`ThemeToggle` and persisted to `localStorage`. Light is the fixed default regardless of system preference — `globals.css` deliberately has no `prefers-color-scheme: dark` block, only the explicit toggle switches to dark. `components/theme/ThemeScript.tsx` is inlined in `<head>` to apply a saved `dark` choice before first paint and avoid a flash — keep it a plain inline script, not a component that renders after hydration.

Logo: `components/layout/Logo.tsx` renders `public/brand/marahil-logo.png` (the full star + book + "مراحل"/"Marahil" lockup) via `next/image`; it's a fixed-color raster now, not a theme-aware inline SVG, so it doesn't recolor across light/dark. `public/brand/marahil-mark.png` is the icon-only crop (no wordmark) used for `app/icon.png`/`app/apple-icon.png` — the full lockup's text isn't legible at favicon size.

### Backend structure (`backend/`)

Just `firestore.rules`, `storage.rules`, and `firestore.indexes.json` — no server code. `firestore.rules` is the actual authorization logic for the whole app; read it before assuming what a client can or can't write.
