# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"مراحل" (Marahil) — an Arabic-language (RTL), interactive tutoring/course platform covering every school stage (kindergarten through university and professional training), with quizzes, progress tracking, gamification (XP/streaks/badges), auto-issued digital certificates with QR-code verification, course ratings, a teacher question bank, and Firestore-only live classroom sessions (whiteboard/chat/poll).

The repo is a monorepo with two independently deployed halves:

- **`frontend/`** — Next.js 16 (App Router, TypeScript, Tailwind CSS v4). Deployed to Vercel with **Root Directory = `frontend`**.
- **`backend/`** — Firebase project config: Firestore/Storage security rules only. Deployed via `firebase deploy` run from inside `backend/` (project id `marahil-2026`, set in `backend/.firebaserc`).
- **`design-reference/`** — a static JSX mockup from an earlier, unrelated concept ("أُفُق"/Ofoq). Kept only as a visual reference; not imported or built by anything.
- **`update.html`** (repo root, ~230KB) — the static HTML/CSS/JS design mockup that the landing/quiz/lesson-locking/gamification redesign was ported from. Kept as a source-of-truth reference for that work, same role as `design-reference/`; not referenced anywhere in `frontend/` build config or app code.

There is no separate Node/Express backend, and **no Cloud Functions** — the project intentionally stays on Firebase's free Spark plan (no billing account attached), so Auth + Firestore + Firestore security rules *are* the entire backend. The one exception is `frontend/src/app/api/upload/route.ts`, a single Vercel serverless API route (see "Image uploads" below) — that's Vercel infrastructure that ships with every Next.js app regardless, not a Firebase Cloud Function, so it doesn't touch the Spark-plan constraint.

## Commands

Run from `frontend/`:
- `npm run dev` — dev server (Next 16 defaults to Turbopack)
- `npm run build` — production build (also runs the TypeScript check)
- `npm run lint` — ESLint

Run from `backend/` (requires `firebase login` once):
- `firebase deploy` — deploys Firestore rules, indexes, and Storage rules together
- `firebase deploy --only firestore:rules` — deploy just the rules (the usual case)

## Architecture

### Data model (Firestore)

- `users/{uid}` — `{ name, email, role: "teacher"|"student"|"admin", photoURL?, xp, streakCount, lastActiveDate, createdAt }`. `role` can only be `"admin"` if another admin (or a human editing Firestore directly in the Firebase Console) set it that way — no client-side `create` path ever allows `role: "admin"`, so the first admin always has to be bootstrapped by hand-editing their `users/{uid}` doc in the Console after they register normally.
  - `users/{uid}/activity/{date}` — `{ count }`, `date` = `"YYYY-MM-DD"`. One doc per day a lesson was completed, used only for the student dashboard's weekly-activity chart — see "Weekly activity, recommendations" below.
- `courses/{courseId}` — `{ title, description, stage, subject, teacherId, teacherName, published, lessonsCount, studentsCount, createdAt, price?, materials?: CourseMaterial[], quiz?: QuizQuestion[] }`. `price` is EGP, display-only (see "Course pricing" below). `quiz` is a course-wide self-assessment quiz, independent of any lesson's own quiz.
  - `courses/{courseId}/lessons/{lessonId}` — `{ title, order, videoUrl?, content?, quiz?: QuizQuestion[] }`. A lesson either has a quiz (graded, drives progress) or is marked complete manually. Lessons are sequentially locked for students — see "Sequential lesson locking" below.
- `enrollments/{uid}_{courseId}` — one doc per student per course; id is deterministic (`uid_courseId`), not auto-generated. Tracks `completedLessonIds`, `quizScores`, `progress` (0–100), `certificateIssued`.
- `certificates/{uid}_{courseId}` — `{ uid, studentName, courseId, courseTitle, teacherName, serial, verifyCode, issuedAt }`. Same deterministic-id scheme as `enrollments`. Publicly readable (verification page needs it).
- `reviews/{uid}_{courseId}` — `{ uid, studentName, courseId, courseTitle, rating: 1-5, comment?, createdAt }`. Same deterministic-id scheme; immutable once created (no client update/delete) — see "Ratings" below.
- `questionBank/{questionId}` — `{ teacherId, question, choices, correct, explanation?, createdAt }`. A teacher's private, reusable MCQ pool — same shape as `QuizQuestion` plus ownership. Never shared between teachers.
- `liveSessions/{sessionId}` — `{ courseId, courseTitle, teacherId, teacherName, title, status: "scheduled"|"live"|"ended", scheduledAt, startedAt?, endedAt?, whiteboardClearedAt, poll?: { pollId, question, options, active } }`. See "Live sessions" below.
  - `liveSessions/{sessionId}/messages/{messageId}`, `.../participants/{uid}`, `.../strokes/{strokeId}`, `.../pollVotes/{uid}`.

### Certificates are issued client-side, but gated entirely by Firestore rules — read `backend/firestore.rules` before touching this

There's no Cloud Function (see above — free plan, no billing account), so `frontend/src/lib/firebase/certificates.ts`'s `issueCertificate()` writes the `certificates` doc directly from the browser once `frontend/src/lib/hooks/useLessonPlayer.ts` sees `enrollment.progress` hit 100. The only thing standing between that and a student forging their own certificate is `backend/firestore.rules`:

- the `enrollments` update rule caps `completedLessonIds.size()` at the course's real `lessonsCount` and only allows `progress == 100` once that count is actually reached, and only allows `certificateIssued` to flip false→true (never back);
- the `certificates` create rule re-derives `studentName`/`courseTitle`/`teacherName` from the real `users`/`courses` docs via `get()` (a client can't write fake display text onto its own certificate), and requires the matching `enrollments/{uid}_{courseId}` doc to already show `progress == 100`.

This is a deliberate trade-off, not an oversight: it's not as airtight as a server-side issuer (a sufficiently motivated user could still pad `completedLessonIds` with fabricated ids up to the real count, since rules can't iterate the `lessons` subcollection to check each id is real), but it needs no billing account. If that gap ever matters, the fix is a Blaze-plan Cloud Function trigger on `enrollments` writes that issues the certificate via the Admin SDK instead — don't try to close it further with more rules; Firestore rules can't enumerate a subcollection's real ids.

If you change how progress/completion is computed, keep the invariant that `enrollments.progress` can only reach 100 in lockstep with the rules' `completedLessonIds.size()` check.

### Sequential lesson locking — enforced in the UI *and* the player, not just hidden links

`frontend/src/lib/utils/lessonAccess.ts` is the single source of truth: `getLessonAccessState(lessons, completedLessonIds)` does one pass over `lessons` (must already be sorted by `.order`) and marks each lesson `"done"` (its id is in `completedLessonIds`), `"active"` (the first not-yet-completed lesson — exactly one per pass), or `"locked"` (everything after it). `isLessonLocked(...)` is a thin wrapper for a single lesson id.

It's enforced in exactly two places, deliberately not just one: `components/courses/LessonList.tsx` uses it to render lock icons and disable links in the lesson list, and `lib/hooks/useLessonPlayer.ts` (which backs the actual `/learn/[courseId]/[lessonId]` page) independently calls `isLessonLocked(...)` before allowing playback — so a bookmarked/guessed URL to a locked lesson can't be played just because the list UI didn't link to it. **Course teachers are exempt from both checks** (`useLessonPlayer` only evaluates lock state `if (!isTeacher)`, where `isTeacher = course.teacherId === uid`) so a teacher can freely preview any lesson in their own course out of order.

`lib/hooks/useContinueLearning.ts` (backing `ContinueLearningCard.tsx` on the student dashboard) reuses the same helper to find the "active" lesson of the student's most-recently-updated in-progress enrollment and deep-links straight to it (falling back to the course page if none is active, e.g. everything locked).

### Gamification (XP, streaks, badges) — client-computed, Firestore-rules-capped, same anti-tamper posture as certificates

**Badges are purely derived, never written to Firestore.** `lib/hooks/useBadges.ts` defines a fixed `BADGES` list, each with a `condition(ctx)` evaluated client-side over already-fetched `profile`/`enrolledCourses`/`certificates` (first lesson completed, first certificate, 3 courses enrolled, a perfect quiz score, a 7-day streak, a fully completed course) — nothing to fake because nothing is persisted.

**XP and streaks *are* persisted (`users/{uid}.xp`, `.streakCount`, `.lastActiveDate`), computed client-side, and only loosely checked by rules — the same trade-off already accepted for enrollment progress and certificates.** `lib/firebase/users.ts`'s `awardLessonCompletionRewards()` runs after every lesson completion (from `useLessonPlayer.completeLesson()`): it adds a flat `XP_PER_LESSON` (10) to `xp`, and bumps `streakCount` by 1 if the gap since `lastActiveDate` is ≤1.5 days or resets it to 1 otherwise. `backend/firestore.rules` doesn't recompute any of this — it only bounds the blast radius of a bad-faith direct write: `xp` must be non-decreasing and can rise by **at most 10 per write** (a literal that must be kept in sync by hand with `XP_PER_LESSON`), `streakCount` may only stay the same, +1, or reset to exactly `1`, and `lastActiveDate` must be non-decreasing. As with certificates, this doesn't prove a lesson was genuinely completed — it just caps how much damage one forged write can do.

### Ratings — computed client-side from `reviews`, deliberately not a stored aggregate on `Course`

`lib/firebase/reviews.ts`'s `createReview()` writes one immutable `reviews/{uid}_{courseId}` doc; `backend/firestore.rules`' `reviews` block requires the matching `enrollments/{uid}_{courseId}` doc to already show `progress == 100` and copies `studentName`/`courseTitle` from the real `users`/`courses` docs via `get()` — the same certificate-issuance pattern, see above. **There is deliberately no `ratingSum`/`ratingCount` counter on `Course`**: Firestore rules evaluate each document in a batch against the *pre-batch* state, so a rule on `courses.update` can never actually prove "a real `reviews` doc was written in this same request" — it can only check the review doc's state *before* the write, which is indistinguishable from "no review was ever written." Any such counter would be a soft security hole. Instead, `lib/hooks/useCourseReviews.ts` (and the browse page's "highest rated" sort) fetch every `reviews` doc for a course and average client-side — same "fine at this project's scale, revisit later" tolerance already accepted for the admin's unpaginated user list. `CourseRatingSummary.tsx`/`RatingStars.tsx` are the read-side display; `ReviewForm.tsx` (rendered from `EnrollPanel.tsx` once `enrollment.progress === 100`) is the one write path, gated on `getUserReview()` finding nothing yet so a student can't be shown the form twice.

### Course pricing — UI/data-model only, no payment gateway

`Course.price` (EGP, undefined/0 = free) is purely informational right now: `EnrollPanel.tsx` shows a price badge, but `enroll()`/`enrollInCourse()` is completely unchanged — enrollment is still free and immediate regardless of `price`, and `enrollments.create` in `backend/firestore.rules` has no payment check at all. If real payment ever gets built, that rule is the actual enforcement point to add a gate to — a price badge alone changes nothing server-side. `TeacherDashboardView.tsx`'s "Estimated Revenue" stat (`price × studentsCount`, summed across a teacher's courses) is explicitly labeled as an estimate, not a wallet or payout schedule — there's no real money movement anywhere in this codebase to back up a payout date.

### Course-level quick quiz — separate from lesson quizzes, never touches progress/certificates

`Course.quiz?: QuizQuestion[]` is authored in `ManageCourseView.tsx` by reusing `QuizBuilder.tsx` as-is (it was already fully generic over `QuizQuestion[]`, no lesson coupling) and saved via `updateCourse()`. `CourseQuickQuiz.tsx` renders it on the course page via `QuizPlayer.tsx` (also already generic) — on a passing attempt it calls `awardLessonCompletionRewards()` directly for a flat one-time XP bonus, which needed **no rules change**: `backend/firestore.rules`' xp cap is per-write, not per-call-site, so it doesn't care that this write didn't come from `useLessonPlayer`. This quiz never writes to `Enrollment` — no progress, no certificate eligibility, purely a self-assessment + small XP nudge.

### Course materials — course-level, not per-lesson; uploaded through a generalized R2 pipeline

`Course.materials?: CourseMaterial[]` (`{ name, url, sizeBytes }`) is edited in `ManageCourseView.tsx` (via `CourseSettingsPanel.tsx`) and shown as a download list in `CourseDetailView.tsx`'s sidebar. Uploading a non-image file needed the R2 upload pipeline to stop being image-only: `lib/upload/uploadConfig.ts` is now the single source of truth for per-folder `{ maxBytes, contentTypes }`, imported by **both** the browser (`uploadFile.ts`, and `uploadImage.ts` is now a thin wrapper around it for existing callers) and the only server-side route in the project, `app/api/upload/route.ts` — the server copy is the one that actually matters for security, the client copy just avoids a round-trip for an upload that would be rejected anyway. `course-materials` allows PDFs/Word/zip (plus images) up to 20MB, versus 5MB images-only for the other three folders. `FileUploadField.tsx` is `ImageUploadField.tsx`'s non-image sibling (filename/size row instead of an `<img>` preview) for any future non-image upload UI.

### Weekly activity, recommendations — client-heuristic panels on the student dashboard, no new infra

**Weekly activity tracks lessons completed per day, not real watch-time minutes** — this app has no video-time-tracking anywhere, so a "minutes" figure would be fabricated; `WeeklyActivityChart.tsx` shows a truthful proxy instead. `incrementDailyActivity()` (`lib/firebase/users.ts`) bumps `users/{uid}/activity/{date}.count` right alongside `awardLessonCompletionRewards()` in `useLessonPlayer.completeLesson()` and `CourseQuickQuiz.tsx`; the matching rule is the same delta-capped-self-write pattern as `xp`/`streakCount` (a write may only start a day at `count == 1` or bump the existing value by exactly 1). `useRecommendedCourses.ts` has no real recommender behind it — it just calls the existing `listPublishedCourses()` per stage the student is enrolled in (or `profile.stage` as a fallback with zero enrollments), excludes already-enrolled courses, and sorts by `studentsCount`.

### Teacher question bank — a private, reusable MCQ pool, separate from any one lesson/course quiz

`questionBank/{questionId}` (`lib/firebase/questionBank.ts`) has the exact same ownership shape as `courses` (a `teacherId` field + `isApproved()` gate on write) but with no `published`/public-read state at all — `backend/firestore.rules`' `questionBank` block only ever lets a teacher read their own. `QuestionBankView.tsx` (`/dashboard/teacher/question-bank`) is the add/delete UI plus a "run trial" button that hands the whole bank straight to `QuizPlayer.tsx` with no `onComplete` side effects (pure practice). **`QuizBuilder.tsx` — reused by lesson quizzes and the course-level quick quiz above — grew an "import from bank" picker** (`ImportFromBankPicker`, opened via `components/ui/Modal.tsx`) that copies selected bank questions in as fresh-id copies; this is the only reason `QuizBuilder.tsx` now imports `useAuth()`/`useQuestionBank()` itself, so it stays a drop-in for every quiz-editing surface without each caller having to wire the picker up separately.

### Live sessions — Firestore-only whiteboard + chat + poll, deliberately no real audio/video

There's no WebRTC/Realtime-Database infra in this project (Spark plan, see above), so `liveSessions` is built entirely on Firestore, including realtime updates — `lib/firebase/liveSessions.ts` is **the first file in the codebase to use `onSnapshot`**, a deliberate, scoped exception to the one-shot-read (`getDoc`/`getDocs`) convention every other `lib/firebase/*.ts` file uses; it stays isolated to live-session code and the `useLive*` hooks that call it.

- **Scheduling**: `TeacherLiveSessionsView.tsx` (`/dashboard/teacher/live`) creates a `liveSessions` doc at `status: "scheduled"`; `startLiveSession()`/`endLiveSession()` flip it to `"live"`/`"ended"`. `backend/firestore.rules` refuses to `delete` a session that's currently `"live"` (end it first). `LiveSessionView.tsx` (`/live/[sessionId]`, a top-level route like `/learn/[courseId]/[lessonId]`) renders one of three states off `session.status`: scheduled (teacher sees a "start" button, student sees the scheduled time), live (the full room), ended (a plain notice).
- **Whiteboard is teacher-draws-only** (`LiveWhiteboard.tsx`) — a deliberate scope decision, not a limitation of Firestore: multi-writer drawing is a real CRDT/conflict problem, and this app's classroom model is one presenter. One immutable doc per stroke (`strokes/{strokeId}`, written once on pointer-up, never per point — `backend/firestore.rules` forbids `update`/`delete` on strokes entirely) holds normalized 0-1 `points` so it redraws correctly at any canvas size. "Clear" doesn't delete stroke docs — it bumps `whiteboardClearedAt` on the session doc itself (already covered by the session's own owner-gated update rule), and `useLiveWhiteboard.ts` just filters `stroke.createdAt > clearedAt` client-side. Two stacked `<canvas>` elements: a base layer redrawn from committed strokes on every snapshot, and a transient live layer for the teacher's own in-progress gesture (cleared the instant the stroke commits).
- **Chat** (`LiveChat.tsx`/`useLiveChat.ts`) is create-only while `status == 'live'` and capped at 500 chars by the rules, not just the UI; messages are immutable (no update path) but the teacher/admin can delete one for moderation.
- **Presence + hand-raise** (`LiveParticipants.tsx`/`useLiveParticipants.ts`) is **heartbeat-based, not real disconnect detection** — no Realtime Database `onDisconnect()` here. A participant doc (id = the participant's own uid) gets its `lastSeen` refreshed every 20s while the room is open; the hook treats anyone silent for 60s+ as offline. The doc is deleted on unmount/leave, and the rules let the owning teacher delete anyone's participant doc too (kick).
- **Polls** live as a single `poll` object *on the session doc itself* (`{ pollId, question, options, active }`) rather than a separate collection — only the owning teacher can write it, via the session's already-owner-gated update rule, so no extra match block was needed. Votes are still their own subcollection, `pollVotes/{uid}` (doc id = uid, same one-vote-per-user trick as `enrollments`/`certificates`/`reviews`), storing the `pollId` they were cast for — a `pollId` is regenerated every time the teacher opens a new poll, so a stale vote from an earlier poll in the same session just stops counting in the tally instead of ever needing to be deleted.
- **Visibility**: reading a session (and everything under it) requires the parent course to be visible the same way `courses` itself works — published, or you're the owning teacher, or admin (`sessionCourse()`/`liveSessionData()` helpers in `backend/firestore.rules`, the latter a top-level function alongside `courseData()`/`userData()` since three different subcollections all need to check the parent session's `status`/`teacherId`).
- Student-facing entry points: `UpcomingLiveSessionsPanel.tsx` on the student dashboard (sessions for enrolled courses, `status` scheduled/live) and `CourseLiveBanner.tsx` on the course page (the single soonest upcoming/live session for that course) — both just query `liveSessions` by `courseId` and filter/sort client-side, no composite index needed.

### Admin role is a Firestore-based bypass, not a Firebase Auth custom claim

There's no Admin SDK (see above), so there's no way to set a real Firebase custom claim from this codebase either — `isAdmin()` in `backend/firestore.rules` just checks `role == 'admin'` on the requester's own `users/{uid}` doc via `get()`, the same pattern `courseData()`/`userData()` already used. It's additive-only (`|| isAdmin()`) on top of every existing rule; no owner-only check was removed. `users` read/update, `courses` read, and `enrollments` read all have an admin bypass. The admin dashboard (`/dashboard/admin/users`) can promote/demote any user's `role`, but can't delete a Firebase Auth account or the user's own admin status from someone else without going through the same role-update path — and nothing here can hard-delete a Firebase Auth account at all (needs the Admin SDK); removing a user fully still requires the Firebase Console.

**Disabling a user is a separate `disabled: boolean` kill switch, not a `status` value.** `status` (`pending`/`approved`) stays scoped to the teacher-approval workflow; overloading it for "disabled" would have thrown away a pending teacher's approval state the moment an admin disabled them. `setUserDisabled()` in `lib/firebase/users.ts` just flips `disabled` on the user's own doc; `isApproved(uid)` in `backend/firestore.rules` now also returns `false` once `disabled == true` (any role), so the exact same rule that blocks an unapproved teacher from creating a course now also blocks a disabled teacher from editing an existing course/lesson and blocks a disabled student from creating or advancing an enrollment — no separate gate to keep in sync. On the client, `isAccountDisabled()` (`lib/utils/userStatus.ts`) is checked in `RoleGuard.tsx` the same way `isPendingTeacher()` already was, redirecting to `/auth/account-disabled` (`AccountDisabledNotice.tsx`, mirroring `PendingApprovalNotice.tsx`) instead of a role's dashboard.

**One account is hardcoded as un-demotable and un-disableable: `eldesouky71@gmail.com`** (`PROTECTED_ADMIN_EMAIL` in `frontend/src/lib/constants.ts`). The real enforcement is `isProtectedAccount()` in `backend/firestore.rules`, which the `users` update rule consults to refuse any write — from any admin, including the account itself — that changes that email's `role`, `disabled`, or `email` field; every other field on it (name, photo, personal details) stays normally admin-editable. Rules can't import the frontend constant, so the email is a literal there too — keep both in sync if it ever changes. Only a human editing Firestore directly in the Firebase Console bypasses this, same as every other rules-enforced constraint in this project.

`AdminUsersView`/`AdminUserRow` also cover the rest of what's achievable for user management without the Admin SDK: role/status/statusFilter + search + sort filtering is all client-side over the one `listAllUsers()` fetch (no pagination — fine at this project's scale, revisit if the users collection gets large); bulk select drives `handleBulkDisable` writing every selected user's `disabled` field in parallel, then calls `refresh()` and bumps a `listVersion` counter used in each row's `key` to force a remount — needed because each row otherwise owns its role/status/disabled as local `useState`, seeded once from props, which a parent-triggered refetch alone wouldn't re-sync; "reset password" just calls the existing `resetPassword()` (`sendPasswordResetEmail`) with the target's email — Firebase sends that regardless of who's signed in, so no special admin path was needed. What's still impossible on Spark and isn't attempted: hard-deleting a Firebase Auth account and sending any email/notification that isn't Firebase's own hosted flow (both need the Admin SDK / Cloud Functions).

**Export is `.xlsx`, not CSV** — `lib/utils/exportExcel.ts` wraps SheetJS (`xlsx` on npm). That package has two open advisories (prototype pollution, ReDoS) with no fix released on the npm registry; both are in the *parser*, and this call path is write-only (builds a workbook from our own trusted data, never parses a user-supplied file), so the actual exposure here is effectively nil — but don't repurpose `downloadExcel()` or add an "import from Excel" feature on top of this same dependency without re-reading those advisories first.

**The admin users list has two presentations of the same row — a real `<table>` (`AdminUserTableRow`) on `md:` and up, `<div>` cards (`AdminUserRow`) below it — both rendered unconditionally in `AdminUsersView.tsx` and toggled purely with `hidden md:block` / `md:hidden`, not a JS breakpoint check.** The table's `joined` column (both the `<th>` and its `<td>`) is further hidden below `lg:` (`hidden ... lg:table-cell`) so a tablet-width table doesn't feel as cramped as a desktop one with the full column set — keep that pair in sync if another column needs the same tablet-width treatment. They'd otherwise duplicate a lot of state and Firestore calls, so both are thin presentational wrappers around `lib/hooks/useAdminUserRowActions.ts` (role/status/disabled local state — still seeded once from `user` at mount, per the `listVersion` remount-key note below — plus every handler: role change, approve, disable/enable, reset password, delete) and share three components: `AdminUserActionsMenu.tsx` (the `⋮` dropdown — a plain `useState` + outside-click listener, not a `ui/` primitive, since only this needs one), `AdminUserIconButton.tsx` (a single-icon button with a `title`/`aria-label` tooltip, `tone: "default" | "danger" | "success"` — approve and disable/enable are these now, not full text pills, to keep both the table row and the mobile card narrow), and `AdminUserDetails.tsx` (the expandable field grid, rendered inline under the mobile card or inside a `colSpan`-ed `<tr>` under the table row). **Role change went through two designs before landing on `AdminRoleBadgeButton.tsx`**: first a visible `<select>` (too wide), then briefly folded into the `⋮` menu as up to three items — now the role `Badge` *itself* is the trigger, opening `components/ui/Modal.tsx` (this project's first real modal — every earlier "pick one of a few things" case used an inline expand or a small anchored dropdown instead; centered overlay, closes on backdrop click or Escape) with all three roles listed, current one checked. Both `AdminUserRow` and `AdminUserTableRow` render the same `<AdminRoleBadgeButton role={role} disabled={locked} onChange={handleRoleChange} />` — don't reintroduce a role `<select>` or menu items for this without removing the badge-button version first, or a row would offer three different ways to do the same thing. Delete still can't fire directly from the `⋮` menu — clicking it only sets `confirmingDelete`, rendered as a confirm/cancel row *outside* the menu (a menu item can't stay open through its own confirmation step, since every item click closes the menu first). If you need a third presentation of a user row, extend the hook, don't fork the logic into it.

`AdminUsersView.tsx`'s filter bar is one compact `rounded-2xl` toolbar — search + three pill `<select>`s (`rounded-full`, `text-xs`, no visible `<label>`, just `aria-label`) + the results count, all in a single `flex flex-wrap` row — not the earlier version's boxed grid with a label above each field and a separate bordered row underneath for the count. If it grows another filter, keep it in this same single-row toolbar shape rather than reintroducing the taller labeled-grid layout.

**`age` is teacher/admin's only *derived* `PersonalDetails` field** — `lib/utils/nationalId.ts`'s `parseEgyptianNationalId()` decodes an Egyptian national ID's embedded birth date (century digit + YYMMDD, positions 1–7) into an age, computed client-side, purely structural (regex + date-range checks) — it deliberately does **not** verify the ID's own check digit, since getting that checksum subtly wrong would reject genuinely valid IDs, which is worse than not checking it at all. `PersonalDetailsForm.tsx` (signup) and `ProfileEditForm.tsx` (settings, `profile.role === "teacher" || "admin"`) both render the `age` `FormField` as a disabled, auto-filled input for teacher/admin and a normal editable one for student — same branch condition (`hasNationalId`), duplicated across the two forms rather than shared, since they don't otherwise share form state. A student never sees a national-ID field at all (none is collected for that role); nothing enforces this at the rules layer, since it's purely a UI/UX choice, not a security boundary.

### Auth flows: email/password, Google, forgot-password, complete-profile

`lib/firebase/auth.ts` has both `registerUser`/`loginUser` (email/password) and `signInWithGoogle()` (`GoogleAuthProvider` + `signInWithPopup`) — enabling the Google provider itself is a one-time manual step in Firebase Console → Authentication → Sign-in method, no code does it. Google sign-in has no role, so a first-time Google user has no `users/{uid}` doc yet; `RoleGuard.tsx` distinguishes this from "not signed in" by checking `firebaseUser` (from `useAuth()`) separately from `profile` — no `firebaseUser` → `/auth/login`, `firebaseUser` but no `profile` → `/auth/complete-profile`, `profile.role` mismatch → the user's own dashboard. `GoogleSignInButton.tsx` (shared by `LoginForm`/`RegisterForm`, since the post-sign-in branch is identical either way) does the same `getUserProfile` check right after sign-in to route directly. `resetPassword()` wraps `sendPasswordResetEmail`; the actual reset UI is Firebase's own default hosted action page, not a custom in-app route — deliberate, to avoid building `oobCode`/`confirmPasswordReset` handling for a Spark-plan project that otherwise has no server code.

`CompleteProfileForm.tsx` pre-fills `name` from `firebaseUser.displayName` and, on submit, passes `photoURL: firebaseUser.photoURL ?? undefined` into `createUserProfile()` — so a first-time Google sign-in's avatar gets copied into the `users/{uid}` doc at account creation. `createUserProfile()`/`updateUserProfileFields()` both route their payload through `withoutUndefined()` in `lib/firebase/users.ts` first — Firestore's `setDoc`/`updateDoc` throw on an explicit `undefined` field, which `photoURL` (absent for email/password sign-ups) and any blank optional detail would otherwise be. **`GoogleSignInButton.tsx` also backfills the photo on every subsequent Google sign-in, but only when the existing profile has no `photoURL` at all** (`updateUserPhoto()`, guarded by `!profile.photoURL`) — covers accounts created before this existed, or any other way one ended up with none, without ever overwriting a photo the user later uploaded to R2 through `ProfileView` back to their Google one.

`/profile` (`ProfileView.tsx`) is a full self-service settings page, not just an avatar/read-only view: `ProfileEditForm.tsx` lets a user edit their own name and role-specific personal details (same per-role field set as the signup wizard's `PersonalDetailsForm.tsx`, but pre-filled and single-step) via `updateUserProfileFields()` — clearing an optional field sends Firestore's `deleteField()` for it rather than silently keeping the stale value, since `updateDoc` just skips over keys with `undefined`. `ChangePasswordCard.tsx` reuses the same `resetPassword()` email-link flow as `ForgotPasswordForm`/the admin's per-user reset button (no re-auth flow needed) and only renders when `firebaseUser.providerData` includes the `password` provider — a Google-only account has nothing to reset.

### Image uploads (course cover, lesson image, avatar) go through Cloudflare R2, not Firebase Storage

`courses.coverImageUrl`, `lessons.imageUrl`, and `users.photoURL` (the last already existed for Google sign-in) can all point at an image in a Cloudflare R2 bucket instead of/alongside the defaults (`coverIcon` stays as the always-present fallback when no cover image was uploaded). `frontend/src/lib/firebase/client.ts` still initializes Firebase Storage, but it's unused — R2 is cheaper and this avoids a second security-rules surface to maintain.

The R2 secret access key can never reach the browser, so uploads go through the app's only server-side code, `app/api/upload/route.ts`: the client asks it for a short-lived presigned PUT URL (`@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` against R2's S3-compatible endpoint), then uploads the file bytes straight to R2 from the browser — the file never passes through the Vercel function, avoiding its request-body size limit. Auth on that route is checked **without the Admin SDK**: it calls Firebase's own public Identity Toolkit REST endpoint (`identitytoolkit.googleapis.com/v1/accounts:lookup`) to verify the caller's ID token, the same "no service account" posture as everywhere else in this project. `frontend/src/lib/upload/uploadImage.ts` is the one client-side entry point every upload UI calls (`components/ui/ImageUploadField.tsx`); don't call `/api/upload` directly from a new call site.

Env vars `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET_NAME` / `R2_PUBLIC_URL` are server-only (no `NEXT_PUBLIC_` prefix — see `.env.example`) and live in Vercel's project env vars plus local `.env.local`, never committed. `next.config.ts`'s `images.remotePatterns` has to list both the R2 public host and `lh3.googleusercontent.com` (Google avatar photos) for `next/image` to render them.

### `SiteChrome` renders one sidebar shell for the whole signed-in experience, not just `/dashboard/*`

**`components/layout/SiteChrome.tsx` — not any per-route layout — decides whether a request gets the public `Navbar`/`Footer` or `DashboardShell` (sidebar + topbar), and it now makes that call for every route in the app, not just `/dashboard/*`, home page included.** A signed-in user with a complete, approved, non-disabled profile gets the sidebar shell everywhere except `/auth/*` (kept plain; mid sign-up isn't "in the app" yet) — `/` briefly stayed exempt too (the sidebar's own `nav.siteHome` link pointing there used to mean "step out of the app," so the app shell showing there stacked the topbar back on top of the marketing Hero), but that was reverted: the sidebar is now deliberately the one nav for the whole signed-in site, home page included, rather than switching chrome per-route — don't reintroduce a `/` exemption without checking this is still what's wanted. `app/[locale]/dashboard/{admin,teacher,student}/layout.tsx` are now just a one-line `RoleGuard` each; they used to also render `DashboardShell` themselves, which would now double it up under `/dashboard/*` since `SiteChrome` already does. The per-role sidebar config (`navItems`, `roleLabel`) moved out of those three layout files into `lib/hooks/useDashboardShellConfig.ts`, a hook keyed off `useAuth().profile.role`, so `SiteChrome` can build the same config regardless of which route triggered it. `Footer.tsx` had to become a client component (`useTranslations` instead of the server-side `getTranslations`) so `SiteChrome` — a client component, since it needs `usePathname()` and `useAuth()` — can conditionally render it.

Because `/` and `/auth/*` keep the public `Navbar` for a signed-in user too, `Navbar.tsx`'s own mobile drawer has to independently stay a complete, correct account menu — dashboard, profile, **and logout** — not a stripped-down version of the sidebar; it was shipped once missing logout entirely (a signed-in visitor landing on `/` had no way to sign out from mobile) and once missing the signed-out `login` link (`startNow` only). Its signed-in section is styled to match `DashboardSidebar.tsx`'s nav-item look (rounded-xl row, icon + label, `hover:bg-surface-2`) even though the two aren't the same component — "unify" here means visual consistency between the two nav surfaces, not merging them into one. The drawer's own trigger button is theme/language-agnostic — those two live only inside the opened drawer now (first thing in it), not duplicated on the always-visible mobile header bar too. That trigger button itself is auth-aware: signed out it's the `Menu`/`X` hamburger; signed in, the closed state shows the profile avatar (or a fallback `User` icon circle) instead — same idea as `DashboardTopbar`'s profile-chip-as-menu-trigger — and only swaps to `X` while the drawer is actually open.

While `loading` (auth still resolving) or for a signed-out visitor, `SiteChrome` falls back to the public `Navbar`/`Footer` — same as `Navbar`'s own existing default-to-signed-out rendering during `loading`, so there's no new flash of the wrong chrome introduced here. A handful of pages (`/profile`, `/courses`, `/verify`, `/certificates/[id]`) still carry their own `<section><Container>` padding from when they were *only* ever reached through the public chrome; when a signed-in user hits them now, that stacks with `DashboardShell`'s own `<main className="p-5 md:p-8">` padding — extra whitespace, not breakage, and an acceptable trade-off for now rather than rewriting every dual-mode page's layout.

`DashboardSidebar.tsx` is fixed-positioned with Tailwind's logical-property utilities (`start-0`, `ms-64`, `ltr:-translate-x-full rtl:translate-x-full` for the mobile off-canvas state) rather than literal `left`/`right`/`margin-right` — this is the same convention `Hero.tsx`/`FinalCta.tsx`/`LessonPlayer.tsx` already use, and matters here specifically because the sidebar has to swap sides between the `ar` and `en` locales. Top to bottom it's: a header row with theme/language + the mobile close button — no logo (that's `DashboardTopbar.tsx`'s job now) — then the nav list, `nav.siteHome` (link back to `/`) first, *above* the role's own `navItems`, then the footer with `nav.profile` above logout. `useDashboardShellConfig`'s per-role `navItems` hold only that role's own pages (dashboard home first, labeled via the shared `nav.dashboard` key so the wording is identical across all three) — **`navItems` deliberately excludes `/` and `/profile`**, both of which (plus logout) are sourced from the `nav` namespace directly inside `DashboardSidebar.tsx` rather than threaded through as props or duplicated per role, so every role is guaranteed the identical links in the identical positions — don't add a `/profile` entry back into a role's own `navItems` array, it'd just show up twice.

`DashboardTopbar.tsx` has no search box (it was admin-only and duplicated the search already on `AdminUsersView` itself — see `dashboardAdmin.users.searchPlaceholder` vs. the now-deleted `dashboardAdmin.topbar` key), no separate hamburger button (the profile chip itself is the mobile sidebar trigger, `onClick={onMenuClick}`; a no-op on desktop, where the sidebar is always visible regardless of the open/close state, so leaving the handler unconditional is harmless), and **no theme/language controls, or a logo, either** — after briefly living here, theme/language moved into `DashboardSidebar.tsx` itself (top — where the logo used to be, before it was removed in favor of them, so they're not duplicated between topbar and sidebar) — `DashboardTopbar.tsx` is now the sidebar's *only* logo. `ThemeToggle`/`LanguageSwitcher` both take a `variant?: "default" | "sidebar"` prop for this — the default styling (`border-border`, `text-dim`) assumes a light surface and reads poorly on the sidebar's dark navy gradient, so the sidebar placement passes `variant="sidebar"` (`border-white/20`, `text-white/70`). Since `SiteChrome` now routes a signed-in user through `DashboardShell` on every route including `/` (see above), this sidebar placement is effectively a signed-in user's only way to change language at all — the public `Navbar`'s own switcher is unreachable for them outside `/auth/*`.

This used to be admin-only (`AdminShell`/`AdminSidebar`/`AdminTopbar`, teacher/student had no sidebar at all, and everyone — including admin — also got the public `Navbar` stacked on top, each with its own mobile drawer and logout: the original "2 sidebars" bug).

The two overview charts (`AdminChart.tsx`, a thin Chart.js wrapper) are built with the `dataviz` skill's method — load that skill again before touching chart colors or adding a new chart, don't hand-pick colors.

### Landing page motion: `framer-motion` for micro-interactions, GSAP ScrollTrigger for scroll reveals, Lenis for smooth scroll — public pages only

`components/landing/ScrollReveal.tsx` wraps a section's repeated children (a features grid, a steps grid, a heading+CTA block) and fades/slides each one up once as it scrolls into view, via `ScrollTrigger.batch` — it treats every *direct child* of the wrapped element as its own staggered target, so wrap only the actual repeated-item container, not a whole section (a step's connecting dashed-line div counts as a target too if it's a sibling inside the wrapped div — harmless, it just fades in with the steps). `gsap.registerPlugin(ScrollTrigger)` is guarded behind `typeof window !== "undefined"` at module scope, and the reveal itself no-ops under `prefers-reduced-motion`. It only ever runs once per mount (no `dependencies` passed to `useGSAP`), so `StagesSection.tsx`'s subject-tag row — which re-renders with different tags on every tab click — is deliberately left *outside* `ScrollReveal`; only its stable tab-button row is wrapped, so switching tabs never fights a one-time reveal animation.

`components/layout/LenisProvider.tsx` wraps only `SiteChrome`'s public-chrome branch (`Navbar`/`Footer`), never `DashboardShell` — Lenis-style scroll smoothing is a known anti-pattern over data-heavy lists/tables, which is most of the dashboard now that the sidebar wraps it. It drives Lenis off `gsap.ticker` (the officially documented GSAP+Lenis integration: `gsap.ticker.add((time) => lenis.raf(time * 1000))`, `gsap.ticker.lagSmoothing(0)`, and `lenis.on("scroll", ScrollTrigger.update)` to keep ScrollTrigger's positions in sync with Lenis's virtual scroll) rather than its own `requestAnimationFrame` loop, so it shares one rAF driver with the ScrollTrigger reveals instead of running a second one. Skipped under `prefers-reduced-motion`, same as `ScrollReveal`.

### Quiz player: lettered choices, countdown timer, animated score ring, confetti + share — `QuizPlayer.tsx`/`QuizQuestionCard.tsx`

Choices render as lettered options (A/B/C/…) rather than plain radio rows; a per-question or per-quiz countdown timer drives auto-advance/auto-submit; the results screen shows the score on `ui/ProgressRing.tsx` (a generic animated SVG progress ring, not quiz-specific — reuse it anywhere else a percentage needs to animate in) plus star rating, and fires the same `canvas-confetti` burst pattern already used for certificates when the score is a pass. "Share result" copies a summary to the clipboard rather than posting anywhere — no backend to post to. `ui/ToastProvider.tsx`/`Toast.tsx` (a new generic toast primitive, not quiz-specific either) backs the share-copied confirmation and is available for any future transient-notification need.

### Motion: `framer-motion` site-wide, `canvas-confetti` on certificates and passing quizzes — no 3D anywhere anymore

`Button.tsx` and `StatCard.tsx` are `motion.button`/`motion.div` under the hood now — **both need their own `"use client"`, independent of whichever page renders them**, since a `motion.*` component throws ("createMotionComponent() from the server") the moment any of its callers sits behind a Server Component boundary without the child itself being an explicit Client Component; the file that defines the `motion.*` usage is what needs the directive, not just its callers. `ButtonProps` also has to `Omit` `onDrag`/`onDragStart`/`onDragEnd`/`onAnimationStart`/`onAnimationEnd` from `ButtonHTMLAttributes` — framer-motion's own gesture-handler props of the same name have an incompatible signature, so spreading native DOM props into `motion.button` fails to typecheck otherwise. `DashboardShell.tsx`'s `<main>` wraps `{children}` in `AnimatePresence`/`motion.div` keyed by `usePathname()` for a fade between pages — this now covers every route the shell wraps (see above), not just `/dashboard/*`.

**The Hero used to have a `three`/`@react-three/fiber` 3D star above the title — it's gone, along with those three packages (and `@types/three`), fully uninstalled.** It was purely decorative and didn't read as anything to an actual viewer; `components/landing/FeaturedCoursesSlider.tsx` now occupies that exact spot with real content instead — the platform's most-enrolled published courses (`usePublishedCourses("all")`, client-sorted by `studentsCount`, capped at 6), auto-advancing (paused under `prefers-reduced-motion`) with prev/next arrows and dot indicators, each slide linking to `/courses/{id}`. Renders nothing at all while loading or if there are zero published courses, rather than showing an empty carousel — don't add a placeholder/skeleton slide for the empty case without checking whether that's actually wanted; the empty-platform state was deliberately left blank here. If `three`/R3F ever comes back for something else, re-read the muddy-brown-light lesson that was learned and then removed along with it: a directional light's color multiplies with a material's own color, so keep scene lights neutral white unless you've actually checked the rendered result.

`CertificateView.tsx` fires a one-time `canvas-confetti` burst (brand colors via `getComputedStyle`, same pattern as `chartColors.ts`) when a certificate finishes loading, skipped under `prefers-reduced-motion`, guarded by a `useRef` so it can't refire on an unrelated re-render. `QuizPlayer.tsx` fires the same style of burst on a passing score (see "Quiz player" above).

GSAP/ScrollTrigger (`components/landing/ScrollReveal.tsx`, scroll-in reveals on the landing sections) and Lenis (`components/layout/LenisProvider.tsx`, smooth scroll) were added in a later pass — see the `SiteChrome`/sidebar section above for why Lenis is deliberately scoped to the public-chrome branch only and kept out of the dashboard.

### Frontend structure (`frontend/src/`)

Small, single-purpose files by convention — prefer adding a new file over growing an existing one.

- `app/[locale]/` — every route is nested under a `[locale]` segment (`ar`/`en`, see i18n below); there is no un-localized `app/` route. Each `page.tsx` is a thin wrapper that awaits `params` (Next 16: `params` is a `Promise`, and now also carries `locale`) and renders one component from `components/`. No business logic in `app/`. Lesson playback lives at `learn/[courseId]/[lessonId]`, not `lesson/` (that name is reserved for the `components/lesson/` group below). `live/[sessionId]` is the equivalent top-level route for a live session room (see "Live sessions" above) — also outside `dashboard/`, gated only by `AuthGate`/Firestore rules like `/learn/*` is. `profile/` (no `[locale]` inside it — it's a locale-scoped route like the rest, just role-agnostic, unlike everything under `dashboard/`) is the one signed-in page not gated by `RoleGuard`. `dashboard/teacher/` also has `question-bank/` and `live/` sub-routes now, both plain pages under the role's own `layout.tsx` (no extra guard needed, same as `courses/new`).
- `app/api/` — server-only route handlers, outside `[locale]` (API routes aren't localized pages). Currently just `upload/route.ts` — see "Image uploads" above before adding another one.
- `components/` — grouped by feature: `landing/` (also `SubjectMarquee`, `AvatarStack`, `TeacherPitch`), `auth/` (also `GoogleSignInButton`, `ForgotPasswordForm`, `CompleteProfileForm`, `PendingApprovalNotice`, `AccountDisabledNotice`, `ContactAdminNotice`, `AuthGate`, `PersonalDetailsForm`), `courses/` (also `RatingStars`, `CourseRatingSummary`, `ReviewForm`, `CourseQuickQuiz`, `CourseMaterialsPanel`, `CourseLiveBanner`), `lesson/`, `quiz/`, `certificates/`, `live/` (`LiveSessionView`, `LiveWhiteboard`, `LiveChat`, `LivePoll`, `LiveParticipants` — see "Live sessions" above), `profile/` (`ProfileView`, `ProfileEditForm`, `ChangePasswordCard`), `dashboard/` (role-shared: `DashboardHeader`, `StatCard`, `DashboardShell`/`DashboardSidebar`/`DashboardTopbar`), `dashboard/teacher/` (also `CourseSettingsPanel`, `QuestionBankView`, `TeacherLiveSessionsView`), `dashboard/student/` (also `BadgesRow`, `ContinueLearningCard`, `XpStreakBar`, `WeeklyActivityChart`, `RecommendedCoursesPanel`, `UpcomingLiveSessionsPanel`), `dashboard/admin/` (also `AdminChart`), `layout/` (also `SiteChrome`), `theme/` (`ThemeToggle`, `ThemeScript`, `LanguageSwitcher`), `analytics/` (`AnalyticsInit`), `ui/` (generic primitives: `Button`, `Card`, `Badge`, `ProgressBar`, `ProgressRing`, `Spinner`, `Container`, `FormField`, `ImageUploadField`, `FileUploadField`, `Modal`, `Toast`, `ToastProvider`).
- `lib/firebase/` — one file per collection/concern (`auth.ts`, `users.ts`, `courses.ts`, `enrollments.ts`, `certificates.ts`, `reviews.ts`, `questionBank.ts`, `liveSessions.ts`, `stages.ts`, `auditLog.ts`, `analytics.ts`, `client.ts` for SDK init). This is the only layer allowed to import from `firebase/*`. `liveSessions.ts` is the one exception to "one-shot reads only" in this layer — see "Live sessions" above.
- `lib/upload/` — `uploadConfig.ts` (per-folder size/type rules, shared with `app/api/upload/route.ts`), `uploadImage.ts` (thin image-specific wrapper) and `uploadFile.ts` (the generic implementation both `uploadImage.ts` and `FileUploadField.tsx` call) — the R2 upload client, see "Image uploads"/"Course materials" above. Not a Firebase concern, so it's deliberately outside `lib/firebase/`.
- `lib/utils/lessonAccess.ts` — sequential lesson-locking logic (see above). Pure functions, no I/O; consumed by both a component and a hook, so keep it dependency-free rather than folding it into either call site.
- `lib/hooks/` — one `useX` hook per screen/concern, each wrapping a `lib/firebase/*` call in loading/state management (e.g. `useCourseDetail`, `useEnrollment`, `useLessonPlayer`, `useTeacherCourses`, `useBadges`, `useContinueLearning`, `useCourseReviews`, `useWeeklyActivity`, `useRecommendedCourses`, `useQuestionBank`, and the `useLive*` family — `useLiveSession`/`useLiveChat`/`useLiveWhiteboard`/`useLivePoll`/`useLiveParticipants`/`useTeacherLiveSessions`/`useUpcomingLiveSessions`/`useCourseLiveSession`). Components call hooks; hooks call `lib/firebase/*`; components never import `lib/firebase/*` directly.
- `context/` — global state: `AuthProvider.tsx` (Firebase auth user + Firestore profile + role, read via `useAuth()`) and `ThemeProvider.tsx` (light/dark, read via `useTheme()`).
- `types/` — one file per domain type (`course.ts`, `user.ts`, `quiz.ts`, `certificate.ts`, `stage.ts`, `review.ts`, `liveSession.ts`).
- `data/stages.ts` — static list of school stages/subjects, used both by the landing page and the course-creation/filter UI. Edit here to add a stage or subject, not in components.
- `data/governorates.ts` — Egypt's 27 governorates (`GOVERNORATE_IDS`), same static-list-plus-translated-label pattern as stages (`lib/hooks/useGovernorates.ts` mirrors `useStages.ts`/`useStageLabel()`). `PersonalDetails.governorate` stores the id (e.g. `"cairo"`), not the label — `useGovernorateLabel()` translates an id back to a label for display (admin user details, the Excel export), and falls back to the raw stored value for pre-existing free-text governorate data written before this was a dropdown.

Role-gating: `components/auth/RoleGuard.tsx` is called once per role, in that role's `dashboard/{admin,teacher,student}/layout.tsx`, and redirects based on `useAuth().profile.role`. There's no middleware-based *auth* protection — it's all client-side via this guard plus the Firestore rules being the real enforcement layer. (`proxy.ts` does exist, but it's `next-intl`'s locale-routing middleware, unrelated to auth — see below.)

**`components/auth/AuthGate.tsx` is the site-wide version of that same three-way check — no profile yet / pending teacher / disabled — mounted once in `app/[locale]/layout.tsx` above `SiteChrome`, not scoped to `/dashboard/*` like `RoleGuard`.** A signed-in user in one of those three states gets redirected off of *any* route except `/auth/*` (so the target pages themselves, and everything under `/auth/`, stay reachable) — not just kept out of the dashboard, kept out of the whole app: browsing `/courses` or even `/` with an incomplete profile bounces you to `/auth/complete-profile` first. `RoleGuard` no longer issues those three redirects itself (to avoid racing `AuthGate` to two different targets on the same tick) — it still blocks *rendering* on the same conditions, so dashboard content doesn't flash before `AuthGate`'s effect fires, but the actual redirect for no-profile/pending/disabled is `AuthGate`'s job everywhere, `RoleGuard`'s only remaining redirects are signed-out → login and wrong-role → the user's own dashboard. `PendingApprovalNotice.tsx`/`AccountDisabledNotice.tsx`/`CompleteProfileForm.tsx` each still redirect *away* from their own `/auth/*` page once its condition no longer applies (e.g. an approved teacher clicking "check again") — that part was never `AuthGate`'s job, since `/auth/*` is exempt from it.

Both of those notice pages also render `ContactAdminNotice.tsx` (a `mailto:` link to `SUPPORT_EMAIL` in `lib/constants.ts`, currently the same address as `PROTECTED_ADMIN_EMAIL` but kept as a separate constant in case support should ever go through a different inbox) — a pending or disabled account needs a way to actually reach the admin, not just be told to.

i18n: routing/UI text is bilingual (Arabic default, English) via `next-intl`. `i18n/routing.ts` defines `locales: ["ar", "en"]`, `defaultLocale: "ar"`, `localePrefix: "always"`; `i18n/navigation.ts` exports locale-aware `Link`/`useRouter`/etc. to use instead of Next's own; `i18n/request.ts` resolves the active locale server-side. `proxy.ts` at the `src/` root (Next 16's rename of `middleware.ts` — same convention, new filename) runs `next-intl`'s middleware to redirect bare paths to a locale prefix. Copy is in `messages/ar.json` and `messages/en.json` — add new strings to both, don't hardcode UI text in components. `app/[locale]/layout.tsx` sets `dir="rtl"|"ltr"` from the locale and loads fonts.

Visual design: the whole app is driven by semantic CSS custom properties defined once in `app/globals.css` (`--bg`, `--surface`, `--heading`, `--body`, `--primary`, `--accent`, `--gold`, `--danger`, `--success`, etc.), re-exposed as Tailwind utilities via a Tailwind v4 `@theme inline` block (so `bg-primary`, `text-heading`, `border-gold/40` etc. just work) — there's no `tailwind.config` theme extension. Components essentially never hardcode a hex color; the only exceptions are `Constellation.tsx`'s canvas-rendering fallback constants, `useQrCode.ts`'s QR-library color option (the `qrcode` package needs literal hex, not `var()`), `GoogleSignInButton.tsx`'s inline Google "G" mark (Google's brand colors are fixed, not themeable), `lib/utils/chartColors.ts` reading the `--chart-1/2/3` tokens via `getComputedStyle` for the same reason (Chart.js draws to canvas, which can't resolve `var()`), and `CertificateView.tsx`/`QuizPlayer.tsx`'s confetti colors (canvas, same constraint — see the Motion section above), and any inline `style={{ backgroundImage: "linear-gradient(..., var(--primary), ...)" }}` gradients that Tailwind utilities can't express — all still source the actual app colors from the same tokens wherever the app's own palette is involved. When adding a new color, add the token to `globals.css` (both the light `:root` block and the `[data-theme="dark"]` block) and its `--color-*` mapping in `@theme inline`, not a one-off arbitrary-value class. The brand palette is deep navy blue (`--primary`, trust/knowledge), teal (`--accent`, growth), and gold (`--gold`, achievement — the star in the logo); see `public/brand/`. `--chart-1/2/3` are a separate categorical triplet just for Chart.js marks — `--primary` itself is too dark to pass a chart mark's lightness band, so don't reuse it there; re-validate with the `dataviz` skill's `validate_palette.js` before changing any of the three.

Fonts: Cairo (Arabic + Latin) is the default for both `--font-display` and `--font-body`; an `html[lang="en"]` override in `globals.css` swaps to Poppins (with Cairo as fallback) for the English locale, per the brand typography spec. Both are loaded via `next/font/google` in `app/[locale]/layout.tsx` — don't reintroduce a manual `@import` for them in CSS (breaks `@import`-must-be-first CSS ordering with Tailwind's own `@import "tailwindcss"`).

Light/dark theme is a `data-theme` attribute on `<html>`, toggled by `ThemeProvider`/`ThemeToggle` and persisted to `localStorage`. Light is the fixed default regardless of system preference — `globals.css` deliberately has no `prefers-color-scheme: dark` block, only the explicit toggle switches to dark. `components/theme/ThemeScript.tsx` is inlined in `<head>` to apply a saved `dark` choice before first paint and avoid a flash — keep it a plain inline script, not a component that renders after hydration.

Logo: `components/layout/Logo.tsx` renders `public/brand/marahil-logo.png` (the full star + book + "مراحل"/"Marahil" lockup) via `next/image`; it's a fixed-color raster now, not a theme-aware inline SVG, so it doesn't recolor across light/dark. `public/brand/marahil-mark.png` is the icon-only crop (no wordmark) used for `app/icon.png`/`app/apple-icon.png` — the full lockup's text isn't legible at favicon size.

### Backend structure (`backend/`)

Just `firestore.rules`, `storage.rules`, and `firestore.indexes.json` — no server code. `firestore.rules` is the actual authorization logic for the whole app; read it before assuming what a client can or can't write.
